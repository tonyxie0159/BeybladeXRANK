# 第一次封測體驗問題修正

## 文件目的

本文件是第一次封閉測試後的修正依據。開發優先順序為登入可靠性、即時同步與通知、對戰流程與介面、賽事與身分規則，最後才進行跨裝置整合驗收。壓力與大量併發測試不列入本輪交付門檻。

## 已確認需求

### 登入、註冊與玩家身分

- 表單只有在前端驗證成功且提交未被取消時才進入「處理中」；驗證失敗、伺服器返回錯誤、瀏覽器返回或快取還原時必須恢復。
- 帳號與玩家名稱都必須唯一，儲存時去除前後空白，英文不分大小寫。
- 玩家名稱可修改，但仍需通過唯一性檢查。
- 邀請及玩家搜尋只顯示玩家名稱，表單傳送內部 UserId，不向其他玩家公開帳號。

### 即時同步與通知

- 使用 SignalR 推送邀請、流程狀態、比分、失誤、重排與賽事變更；同流程玩家立即導向正確頁面。
- 重新連線、頁面回到前景或手機解除休眠時立即向伺服器核對狀態，低頻輪詢只作為備援。
- 全站右上角提供通知鈴鐺；未讀時顯示驚嘆號並提供可存取的未讀數量。
- 邀請與待辦先顯示六秒提示，可直接接受或前往處理。提示消失不等於已讀。
- 邀請的接受、拒絕、取消與失效都要通知邀請者。逐次計分只推送即時狀態，不建立永久通知。
- 本輪只提供站內通知，不包含作業系統推播。

### 對戰流程

- 勝利方式提交後，在同一交易中記錄結果、完成本局並建立下一局；移除逐局「確認計分」。
- 達到目標分數後仍需一次「確認結束對戰」。
- 修改較早局數時保留原紀錄及稽核資料，將所有後續局標記為失效，重新計分後從下一站位開打。
- 快速對戰與賽事對戰使用同一修訂規則；賽事既有的下游場次保護不得繞過。
- 重排頁預設帶入上一輪出戰順序，雙方都必須即時進入重排及下一輪。

### 裁判與對戰介面

- 計分板上方顯示 B Side 與 X Side 的玩家名稱，失誤顯示在各玩家下方。
- 當前局只顯示 Round、藍色 B Side 陀螺及紅色 X Side 陀螺，不在每筆紀錄重複玩家與失誤。
- 勝利方式置於計分板下方；「對戰紀錄」、「判決修改」、「對戰處理」同列。
- 棄權與取消只在展開「對戰處理」後顯示。
- 完整對戰紀錄使用獨立頁面，包含局結果、失效紀錄與修訂歷史，並可回到比賽。
- 完賽頁提供回到首頁；賽事對戰另提供返回賽事。

### 賽事

- 所有使用者可見的賽制與狀態都以繁體中文及一致的語意色彩呈現，不直接輸出 Enum。
- 賽制名稱為單淘汰、雙敗淘汰、單循環、瑞士輪。
- 單人賽鎖定個人報名；團體賽只提供隊伍報名與由系統自動組隊。
- 邀請使用玩家名稱模糊搜尋：一個字起查、250ms 防抖、最多十筆，排除本人與不符合資格者。
- 賽事時間只顯示建立、正式開始、完成。
- 賽程只顯示順序、出戰隊伍、對戰結果；不顯示內部 Round/Match 代碼。
- 輪空只晉級，不計勝敗；不戰勝計一勝一敗，但不建立比分及得失分。
- 尚未有有效對局時勝敗皆為零。
- 主排名只顯示名次、參賽者或隊伍、勝敗、總得失分；直接對戰、同分群組差與瑞士輪依據置於展開說明。
- 依模式使用「參賽者」或「參賽隊伍」，列表顯示成員與目前勝敗。

## 資料與公開介面

- 新增 `UserNotification`、通知種類與安全動作種類，保存目標使用者、內容、關聯實體、防重複鍵及建立／已讀／完成時間。
- `User` 新增 `NormalizedAccount` 與 `NormalizedDisplayName` 唯一索引。
- SignalR 端點為 `/hubs/realtime`，只依已驗證 UserId 加入私人群組。
- `/Notifications` 提供通知中心、未讀摘要、接受動作及單筆／全部已讀。
- `/Players/Search?q=` 只回傳 UserId 與玩家名稱。
- 對戰服務提供交易式 `RecordAndCompleteRoundAsync`，並新增因較早判決修訂而失效的稽核原因。

## 開發順序

1. 修正表單狀態及登入、註冊回歸測試。
2. 建立通知資料、SignalR、全站鈴鐺、六秒提示與重連同步。
3. 串接快速對戰、組隊、賽事邀請及同流程導頁。
4. 合併逐局計分、完成修訂截斷、重排預設與裁判／紀錄介面。
5. 完成賽事中文化、建立表單、玩家搜尋、唯一名稱、排名與輪空規則。
6. 套用 migration，備份並確認實際資料庫路徑後重置封測資料。
7. 以兩個獨立登入工作階段進行手機寬度完整流程驗收。

## 驗收條件

- 錯誤表單提交後無需重新整理即可再次提交。
- 邀請、比分、重排、開始與完賽不依賴手動刷新。
- 斷線重連與頁面回到前景後狀態自動補齊。
- 重複提交不會重複計分、建局或產生重複通知。
- 修改早期局數後，失效的後續資料不參與比分與戰績。
- 輪空不計勝敗；不戰勝只計勝敗、不計得失分。
- 未進行對局的賽事不再預設勝場。
- 使用者畫面不出現原始英文 Enum 或內部輪次代碼。
- 每個 PR 交付前執行 `dotnet test BeybladeXRANK-main/BeybladeRecordSystem.slnx`。

## 資料安全

封測資料重置必須在 migration 與測試完成後執行。執行前停止應用程式、解析並驗證實際資料庫絕對路徑、備份資料庫與 WAL/SHM；只處理已確認的作用中資料庫，不刪除歷史備份或來源不明的資料庫。

## 仍需實機人工驗收

- 兩支手機使用不同帳號，驗證邀請、選螺、開始、計分、重排、下一輪與完賽全程不需手動刷新。
- 將其中一支手機切到背景、鎖定再解除，或暫時斷網，驗證重連後能立即補齊狀態且不重複計分／通知。
- 驗證快速、組隊及賽事邀請的接受、拒絕、取消與失效：六秒提示、鈴鐺未讀、通知中心、已讀與導頁均正確。
- 打完至少三局後修改第一局，確認後續局保留於紀錄但標示失效、比分重算，雙方從正確站位重新開打。
- 完成一組後驗證雙方同時進入重排，且都預設帶入上一輪原始出戰順序。
- 以手機寬度檢查計分板、對戰處理展開、完整紀錄、賽程表、排名依據與參賽者／隊伍列表的觸控與可讀性。
- 完成至少一場單人賽與一場團體賽，確認輪空不計勝敗、不戰勝只計一勝一敗且不產生得失分。

壓力、大量併發與長時間連線測試依本輪決策延後，不阻擋第一次封測流程修正。
